  <a href="https://developer.monday.com/api-reference/docs/release-notes#2027-01"
     style="color: #ffffff; text-decoration: underline; font-weight: 600;">
     2027-01
  </a>
</div>`}</HTMLBlock>

**Breaking change.** In API version 2027-01, the `activity_logs` field on `Board` is rebuilt around cursor-based pagination, richer filters and a 90-day window. The field no longer returns a plain list of `ActivityLogType` entries. It now returns a `BoardActivityLogsPage` object that holds the page of entries and a cursor for the next page.

What changed for the `activity_logs` field on the [Board](https://developer.monday.com/api-reference/reference/boards) type:

* **New return shape.** The field returns `BoardActivityLogsPage` with `logs` (a list of `ActivityLog` entries) and `cursor` (pass it back to fetch the next page; it is `null` on the last page). `ActivityLog` entries also expose `correlation_id`, `triggering_flow_id` and `triggering_flow_type`, which group entries that belong to the same logical session or triggering flow, such as an agent run.
* **Cursor replaces `page`.** The `page` argument is removed. Use the new `cursor` argument instead.
* **New filters.** `event_types` filters by event type (for example `create_pulse`), `correlation_ids` returns the events that belong to the same logical session, and `search` runs a free-text prefix search over item names.
* **90-day window.** The `from` argument accepts timestamps up to 90 days in the past. A request for older data returns a validation error.
* **Argument types changed.** `from` and `to` are now `String` (ISO 8601) instead of `ISO8601DateTime`. `column_ids` and `group_ids` are now `[ID!]` instead of `[String]`.
* **`limit` default.** The schema no longer declares a default value for `limit`. Its description states a range of 1-1000 and a default of 25.

Example request that reads the first page and the cursor for the next one:

```graphql
query {
  boards(ids: [1234567890]) {
    activity_logs(
      from: "2027-01-05T00:00:00Z"
      event_types: ["create_pulse"]
      limit: 50
    ) {
      logs {
        id
        event
        entity
        user_id
        created_at
        data
      }
      cursor
    }
  }
}
```

## Migration notes

If you query `activity_logs` on API version 2027-01, update your requests as follows:

1. Add the new selection structure. Select `logs { ... }` and `cursor` inside `activity_logs { ... }` instead of selecting entry fields directly.
2. Replace `page` with `cursor`. Send the `cursor` value from the previous response to fetch the next page, and stop when it is `null`.
3. Declare the `from` and `to` variables as `String` instead of `ISO8601DateTime`, and declare `column_ids` and `group_ids` variables as `[ID!]`.
4. Keep `from` within the last 90 days. Requests for older data return a validation error.
5. If you generate types from the schema, regenerate them: the field now returns `BoardActivityLogsPage`.

Earlier API versions are not affected by this change in behavior. Their `activity_logs` field description now warns that the field changes starting from version 2027-01.

# Manage user tokens and credentials

Using the **credentials** app feature, you can effortlessly connect to third-party services—minimal coding required!

Whether you're building blocks for monday workflows or integrating external APIs, this feature makes secure, scalable integrations easier than ever. The framework handles authentication flows and credential storage, so you can focus on building flexible, user‑friendly solutions.

# Concepts

The credentials app feature enables secure authentication between monday apps and third-party services, such as Google, Dropbox, or Slack, within **monday workflows**.

It supports both OAuth 2.0 and API Token authentication flows, making it easy to integrate services regardless of the authentication method they support.

Once authenticated, user-specific credentials are securely stored and scoped to the app. These credentials can then be reused across multiple workflow app features, including blocks and custom fields.

## Security

All credentials are handled with strict security controls:

* Secrets are stored in secure storage.
* Secrets are stored in the same region as the monday.com account region.

> 👍 Authentication types supported
>
> * **OAuth 2.0**: Handles redirect flows, token exchange, refresh tokens, and user consent.
> * **API Token:** Uses a static token for direct API access. Simple and fast to set up, but less secure.
>
> ✅ **Best practice:** Prefer OAuth whenever possible for stronger security and better token management.

## Provider unique identifier

Some third‑party services use unique identifiers to recognize individual user connections.

> :point\_right: For example: In Gmail, the unique identifier is the user's email address.

Since there's no standard for exposing or retrieving the identifier across different services, you must provide a publicly accessible backend endpoint that we can call to retrieve it. This endpoint should verify the incoming request by checking the `Authorization` header against the application signing secret.

```typescript
// Example: Verify Authorization header using the jsonwebtoken package

const { authorization } = req.headers;

const signingSecret = process.env.MONDAY_SIGNING_SECRET;

await new Promise((resolve, reject) => {
   jwt.verify(authorization, signingSecret, (err, decoded) => {
      if (err) {
        reject(err);
      } else {
        resolve(decoded);
      }
   });
});
```

After implementing your endpoint:

1. Navigate to the *Extra details* section of your credentials app feature.
2. Enter the URL of the endpoint used to retrieve the provider’s unique identifier — e.g., `https://your-server`

This refers to the request monday.com sends to your backend during the OAuth callback phase. After the OAuth flow is complete, we’ll call your provided endpoint to retrieve the provider’s unique identifier for the user's credentials.

We include the user's access token in this request, along with the following payload:

```json Header
{
  "token": "abcs1234"
}
```
```json Expected request payload to retrieve provider's unique identifier
{  
  "userId": 123, // The ID of the user initiating the request  
  "accountId": 456, // The ID of the account associated with the request  
  "appFeatureReferenceId": 789, // The reference ID of your app feature  
  "callbackRequestedParams": {...}, // Parameters extracted from the OAuth callback  
  "tokenRequestedParams": {...}, // Parameters extracted from the token response  
  "userCredentialsParams": {...} // Optional parameters provided by the user  
}
```

We automatically enrich the request with the user’s access token, using the key you provided under the `token` key.

## Configure credential parameters

Some third‑party services require user‑specific information (e.g., subdomain, region, organization ID) before initiating the authentication flow. Using credential parameters, you can collect this information and define extra input fields that appear when a user sets up the integration.

> :point\_right: For example: In Salesforce, we need to know the user's subdomain to be able to interact with the correct API.

### Supported types

Credential parameters support primitive data types: `string`, `boolean`, and `number`.

You can link a parameter to a field type that uses one of these primitive types. Parameters can also reference a primitive field type that includes static options.

### How to configure

1. You can configure credential parameters directly in the Developer Center under your *Credentials* app feature. When adding a parameter, be sure to include:

* **Name:** A short key used to reference the value in API calls
* **Title:** A user‑facing name that explains what the field is
* **Type:** Choose from `string`, `number`, or `boolean`
* **Required:** Mark whether the field is required

2. Once configured, these parameters can be referenced inside the other credential fields through a `{{parameterName}}` syntax.

```json Salesforce subdomain example
"authorizationUrl": {
  "type": "url",
  "value": "https://{{subdomain}}.salesforce.com/oauth2/authorize"
}
```

3. When the authorization flow is initiated, we replace the parameters with user‑provided input. That value is also available in the payload of your provider's unique identifier endpoint and other credential‑based requests (e.g., block execution URL, and remote options).

***

## Configure API token parameters

Some third-party services don’t support OAuth and instead require authentication using API tokens. Through API token parameters, you can define the input fields that appear when a user sets up the integration.

### How to configure

You can configure API token parameters directly in the Developer Center under your *Credentials* app feature.

These parameters appear automatically when you select API Token as the credentials type. Some fields are pre-defined and can't be modified, but you can configure the following settings to customize how the token behaves in your app:

* **Parameter Title:** The field title shown to users
* **Placeholder:** The text displayed inside the input field before the user enters a value
* **Static Suffix:** The optional text displayed after the input field
* **Description Text:** Brief additional context or guidance to help users understand what to enter
* **Link Text:** The label for an optional link (e.g., “Learn more”)
* **Link URL:** The destination URL opened when a user clicks the link text

These settings control how the API Token field appears in the monday.com UI when users connect your app.

# Authentication

Learn about monday platform API token permissions, how to access tokens, and how to authenticate requests

The monday.com platform API utilizes **personal V2 API tokens** to authenticate requests and identify the user making the call. These tokens are unique to each user and have no explicit length.

Personal tokens allow you to interact with the API using your own user account. Their permissions mirror what you can do in the monday.com UI, ensuring that API access is consistent with your platform-level permissions.

If you don't have a monday.com account yet, create a free [developer account](https://developer.monday.com/api-reference/docs/developer-sandbox) to get an API token and start testing.

# Token permissions

Personal tokens mirror all permission levels set in the monday.com UI, including [board](https://support.monday.com/hc/en-us/articles/115005315809-Board-permissions), [column](https://support.monday.com/hc/en-us/articles/360011926640-Column-permissions), [item](https://support.monday.com/hc/en-us/articles/360021172320-Item-viewing-permissions-), or [account](https://support.monday.com/hc/en-us/articles/360003457320-Account-permissions) access.

> For example: If you don't have permission to access a certain workspace via the UI, you won't have permission using your personal API token either.

App tokens have an additional [set of permission scopes](https://developer.monday.com/apps/docs/oauth#set-up-permission-scopes) that specify which queries and mutations it can access, while personal tokens have all permission scopes.

# Accessing your token

You can access your API token in two ways, depending on your [user type](https://support.monday.com/hc/en-us/articles/360002144900-User-types-explained).

## In the Developer Center (all users)

All [users with API access](https://developer.monday.com/api-reference/docs/basics#who-can-use-the-api) can follow these steps to access their API token:

1. In your monday.com account, click on your profile picture in the top right corner.
2. Select **Developers**. This will open the *Developer Center* in another tab.
3. Click **API token** > **Show**.
4. Copy your personal token.

<Image align="center" className="border" width="700px" border={true} src="https://files.readme.io/d8a190b958dd51496ca9b1b92de1b660e9ccba227534c642552994b5b3874880-API_Token_in_Developer_Center.png" />

## In the Administration tab (account admins only)

Account admins can use the *Developer Center* steps above or access their token via the *Administration* tab:

1. In your monday.com account, click on your profile picture in the top right corner.
2. Select **Administration** > **Connections** > **Personal API token**.
3. Copy your personal token.

<Image align="center" className="border" width="700px" border={true} src="https://files.readme.io/b8eef71025582992cbb2ab39e60a484431e303a7e409f974979468a6fa4596bc-API_Token_-_Admin.png" />

# Making requests with your token

Once you have your token, you can make requests with the API by passing the token in the `Authorization` header.

```curl cURL
curl -X POST https://api.monday.com/v2 \
  -H "Authorization: xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{"query": "query { me { id name } }"}'
```

# Regenerating a token

API tokens can be regenerated at any time. However, this will immediately invalidate your current token, so be sure to update any integrations using it.

## How to regenerate a token

### In the Developer Center

1. In your monday.com account, click on your profile picture in the top right corner.
2. Select **Developers**. This will open the *Developer Center* in another tab.
3. Click **API token** > **Regenerate**.

### In the Administration tab

1. In your monday.com account, click on your profile picture in the top right corner.
2. Select **Administration** > **Connections** > **Personal API token**.
3. Click **Regenerate**.

# Error handling

If your API request cannot be completed successfully, you will receive an error message.

# Error format

Errors returned by the API have the following characteristics:

* **HTTP status:** Response will be `200 – OK` for application-level errors. Other statuses will be returned for transport-layer errors, such as `500 - Internal server error`, `429 - Too many requests` or `400 - Bad request`
* **JSON response:** Body will contain an `errors` array with further details about each error
* **Partial data:** Requests will return partial data, so the `data` object may also contain some information. For example, if you query three fields, you may receive two fields and one error.
* **`Retry-After` header:** Errors will include the `Retry-After` header to indicate how long you need to wait before making another request
* **[Rate limit headers](https://developer.monday.com/api-reference/docs/rate-limits#rate-limit-headers):** Every response includes `RateLimit-Policy` and `RateLimit` headers that report the current state of your rate limits, so you can monitor your remaining quota proactively
* Each API response includes a `request_id` in the extensions object that can be used for troubleshooting.

### Sample format

Here's an example of an application-level error:

```json Error only

  "data" : [],
  "errors": [

      }

}
```

# Authenticate with an API token

Connect to the monday.com hosted MCP server with a personal API token for personal use, prototyping, and testing

If you're using one of the [compatible MCP clients](https://developer.monday.com/api-reference/docs/compatible-mcp-clients), you don't need a token — add the server URL and authenticate via OAuth when prompted. Use a personal API token when your client **isn't** a compatible MCP client or doesn't support the MCP OAuth flow — for example, custom scripts, homegrown agents, or tools that only support static Bearer tokens.

For personal use, prototyping, and testing, this is the fastest way to connect. No app or registration is needed.

# Get your token

1. Log in to your monday.com account
2. Click your profile picture in the top-right corner and select **Developers**
3. Click **My access tokens** in the left menu
4. Copy your personal access token

# Configure your MCP client

Pass the token as a Bearer token in the `Authorization` header of your MCP requests:

```
Authorization: Bearer YOUR_API_TOKEN
```

For MCP clients that support custom headers, the configuration looks like this:

```json
{
  "mcpServers": {
    "monday-mcp": {
      "url": "https://mcp.monday.com/mcp",
      "headers": {
        "Authorization": "Bearer YOUR_API_TOKEN"
      }
    }
  }
}
```

Personal tokens mirror your UI permissions, so the MCP server can access everything your user can — and nothing more. This is ideal for individual development, but not for integrations used by other people.

<Callout icon="⚠️" theme="warn">
  ### Warning

  Never share your API token or commit it to version control. Rotate tokens regularly, and revoke them when they're no longer needed.
</Callout>

# Control MCP access with your own OAuth app

Replace the hosted MCP connector with your own OAuth app to control who connects, which clients can connect, and which permission scopes the MCP connection can use

By default, connecting an AI assistant (like Claude) to monday.com uses our hosted MCP connector — your users click **Connect**, sign in, and they're done. It's the fastest way to get started, but it's all-or-nothing: once it's enabled, any user who can log in, from any MCP-compatible client, can connect — and the connection inherits that user's full monday.com permissions.

If your organization needs tighter control — for example, allowing only Claude (not other AI tools), limiting access to a specific group of users, or restricting what the MCP connection is allowed to do — you can replace the hosted connector with your own OAuth app. This gives you the same MCP functionality, but with control over who connects, what connects, and which [permission scopes](https://developer.monday.com/apps/docs/oauth#set-up-permission-scopes) apply to the connection.

This is also the right path while you're **developing** a user-facing MCP integration or distributing it privately inside your organization. To let other monday.com accounts connect your client, use [dynamic client registration](https://developer.monday.com/api-reference/docs/mcp-dynamic-client-registration). The customer's admin approves the additional connection and its redirect URIs through [dynamic connectors](https://developer.monday.com/api-reference/docs/mcp-dynamic-connectors).

This guide walks you through the setup. For client-specific walkthroughs, see:

* [Integrating monday MCP with Claude using a Custom App](https://developer.monday.com/api-reference/docs/integrating-monday-mcp-with-claude-custom-app)
* [Integrating monday MCP with Copilot Studio using a Custom App](https://developer.monday.com/api-reference/docs/integrating-monday-mcp-with-copilot-studio-custom-app)

The same credentials work with other MCP clients that support custom OAuth connectors.

# How it works

Instead of relying on monday.com's shared hosted connector, you:

1. Register your own OAuth app in the monday.com developer platform and get a Client ID and Client Secret
2. Turn on **New OAuth flow** under **Build → OAuth & Permissions** — required to connect to MCP with a custom app
3. Turn off the hosted MCP connector for your account
4. Give the app's credentials only to your approved users, who add monday.com as a custom connector in their AI agent, pointing at the same MCP endpoint

Your app now controls the connection — not the shared hosted integration.

# Why do this

* **Control scopes.** Set the OAuth permission scopes on your app — for example `boards:read` only, or no write access. Those scopes limit what the MCP connection can do, even if the authenticated user has broader permissions in monday.com.
* **Choose who connects.** Only users you've given your Client ID and Client Secret to can authorize the connection. Everyone else is locked out, even if they're logged in to monday.com.
* **Choose what connects.** Restrict access to a specific AI client rather than any MCP-compatible tool.
* **Revoke without disruption.** Remove a single user's access, or rotate your Client Secret to cut off everyone at once — without affecting your other integrations.
* **Get your own audit trail.** Your app has its own list of authorized users and activity in the developer platform, separate from the shared hosted connector.

<Callout icon="💡" theme="info">
  **Tradeoff:** Setup takes a few extra steps per user compared to one-click connect, and you're responsible for storing and rotating your Client Secret securely.
</Callout>

***

# Setup steps

## Step 1: Create your OAuth app in monday.com

The monday MCP server uses the standard **OAuth 2.0 Authorization Code Grant**, with monday.com as the identity provider — the same flow used by all third-party integrations with the platform API.

### Create your app

1. Log in to your monday.com account. Click your profile picture in the top-right corner and select **Developers** to open the Developer Center
2. Click **+ Create app** in the top-right corner
3. Enter an **App Name** and **App Slug**, then click **Create app**

### Configure OAuth settings

1. In the left sidebar under **Build**, click **OAuth & Permissions**
2. Open **New OAuth flow** and switch the toggle **on**. You must turn this on to connect to MCP with a custom app — while the toggle is off, the app cannot authenticate to the MCP server
3. On the **Scopes** tab, select only the [permission scopes](https://developer.monday.com/apps/docs/oauth#set-up-permission-scopes) your integration needs — these scopes cap what the MCP connection can do, even when the user has broader permissions in monday.com (add all during testing)
4. Switch to the **Redirect URLs** tab and add your callback URL — the URL where monday.com sends authorization codes — then click **Save**

<Callout icon="🚧" theme="warn">
  **New OAuth flow must be on.** Find it on your app under **Build → OAuth & Permissions → New OAuth flow**. Switch the toggle on before you connect. A custom app cannot connect to MCP while this toggle is off.
</Callout>

### Retrieve your credentials

1. Go to **General Settings** in the left sidebar of your app
2. Scroll down to the **App Credentials** section and copy your **Client ID** and **Client Secret**

<Callout icon="❗️" theme="error">
  ### NOTE

  Your client secret is a _secret_. Never share it or add it to source code others can access. You can regenerate it from the app's settings if it's ever compromised.
</Callout>

## Step 2: Turn off the hosted MCP connector

In your monday.com admin settings, disable the built-in hosted MCP connector. This step matters: as long as it's on, users can bypass your app and connect the old way.

## Step 3: Add a custom connector to your agent

Point your AI agent at the monday MCP server using your OAuth app credentials — not the hosted one-click connector.

You can do this in either of two ways:

* **Configure it yourself** — If you're building or hosting your own MCP client, pass the MCP server URL plus your Client ID and Client Secret into your client's OAuth configuration. See [Authorization flow (custom MCP clients)](#authorization-flow-custom-mcp-clients) for how the token handshake works.
* **Use a product that supports custom MCP connectors** — Tools like Claude, ChatGPT, Copilot, Cursor, and other [compatible MCP clients](https://developer.monday.com/api-reference/docs/compatible-mcp-clients) typically let you add a new MCP connector and supply OAuth credentials. Look for settings such as **Connectors**, **Custom connector**, or **Add MCP server**, then enter:
  * **MCP server URL:** `https://mcp.monday.com/mcp`
  * **OAuth Client ID** and **OAuth Client Secret** from Step 1

<Callout icon="⚠️" theme="warn">
  Only share the URL, Client ID, and Client Secret with users you want to authorize.
</Callout>

### Example: Claude

For screenshots and step-by-step Claude UI instructions, see [Integrating monday MCP with Claude using a Custom App](https://developer.monday.com/api-reference/docs/integrating-monday-mcp-with-claude-custom-app).

### Example: Copilot Studio

For Copilot Studio MCP tool setup (OAuth URLs, redirect URI, naming rules), see [Integrating monday MCP with Copilot Studio using a Custom App](https://developer.monday.com/api-reference/docs/integrating-monday-mcp-with-copilot-studio-custom-app).

## Step 4: Verify

Have one user complete the OAuth flow and confirm the connection appears under your app (not the hosted connector) in the monday.com developer platform.

# Authorization flow (custom MCP clients)

If you're building your own MCP client (rather than using a product's custom connector UI), the authorization flow follows the standard monday.com [OAuth flow](https://developer.monday.com/apps/docs/oauth):

1. Your MCP client redirects the user to `https://auth.monday.com/oauth2/authorize` with your client ID
2. The user approves the requested permission scopes
3. Your client exchanges the authorization code for an access token
4. Include the access token in the `Authorization` header of your MCP requests:

```
Authorization: Bearer YOUR_ACCESS_TOKEN
```

All MCP tool calls execute in the context of the authenticated user, limited by both that user's platform permissions and the scopes enabled on your OAuth app. The MCP token can't exceed either boundary — it doesn't grant permissions the user lacks, and it can't use permissions the app didn't request.

***

***

# Which approach should you use?

| Approach             | Best when                                                                                                                                               |
| :------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Hosted connector** | You want a fast rollout and any authenticated user, from any AI client, with that user's full permissions, is an acceptable level of access             |
| **Custom OAuth app** | You need to limit MCP actions with app scopes, name exactly who can connect, restrict it to a specific client, or need independent audit and revocation |

You can use both across your organization — for example, hosted for general workspaces, and a custom app for workspaces with sensitive data.

# Enterprise managed auth

Let your organization connect an AI client to monday MCP once, through your identity provider, with no per-user OAuth consent.

monday MCP supports enterprise managed auth (EMA), the [Enterprise-Managed Authorization](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization) extension of the MCP specification. With EMA, your organization connects an AI client to monday MCP once, for everyone, and members don't see a monday.com consent screen. When the client needs monday.com, it asks your identity provider (IdP) for a signed identity assertion for the signed-in member. monday.com exchanges that assertion for an access token for the same member.

EMA changes how a connection is approved, not what it can do. Every tool call runs as the member, with their existing monday.com permissions.

# Supported setups

| Identity provider | AI clients | Setup guide                                                                      |
| :---------------- | :--------- | :------------------------------------------------------------------------------- |
| Okta              | Claude     | [Set up enterprise managed auth with Okta](https://developer.monday.com/api-reference/docs/mcp-enterprise-managed-auth-okta) |

Other identity providers and AI clients aren't supported yet.

***

# How monday.com trusts an assertion

There is nothing to turn on in monday.com. monday.com accepts an assertion only when it comes from the IdP app that already runs your account's single sign-on (SSO), and only for a member that SSO has linked to that IdP user. An assertion from any other IdP org or app is rejected.

# Requirements

* **Plan and SSO:** an Enterprise plan account that signs in with [SAML single sign-on](https://support.monday.com/hc/en-us/articles/360000460605-SAML-Single-Sign-on-SSO-) through a supported IdP, with the SSO connection active.
* **Members:** each member is an active monday.com member or admin (not a viewer), has accepted their invitation, and has signed in to monday.com through SSO at least once. The first SSO sign-in links the member's monday.com user to their IdP user. Members created through SCIM are linked only after their first SSO sign-in.
* **AI client:** a client that supports EMA with your IdP. See [Supported setups](#supported-setups).

# Values for your setup

Every IdP and AI client setup uses these values:

| Setting                                          | Value                                                                                                         |
| :----------------------------------------------- | :------------------------------------------------------------------------------------------------------------ |
| Authorization server issuer (assertion audience) | `https://auth.monday.com/mcp`                                                                                 |
| Resource (MCP server)                            | `https://mcp.monday.com/mcp`                                                                                  |
| Scopes                                           | All monday.com scopes, or none. EMA grants the full monday.com scope set, so a partial selection is rejected. |
| Access token lifetime                            | 24 hours. No refresh token is issued; the client gets a new assertion from your IdP instead.                  |

***

# Turn it off

* **For everyone:** turn off EMA for the monday.com connector in your AI client, or remove the connection between the AI client and monday.com in your IdP.
* **For one member:** unassign the member from the monday.com app or the AI client in your IdP.

These changes stop new connections within a few minutes. An access token that monday.com already issued stays valid until it expires, up to 24 hours.

***

# Troubleshooting

When monday.com rejects a connection, the error description usually says what to fix. These need more context:

| Error description                                                                 | What to do                                                                                                                                                                                                                                               |
| :-------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `The assertion is invalid`                                                        | Check your IdP configuration against the [values for your setup](#values-for-your-setup), especially the issuer, audience, client ID, and resource. Some IdP setups also report account and member problems with this error. See your IdP's setup guide. |
| `No monday user with this email is in an account that uses this Okta app for SSO` | Check that the member's email is the same in monday.com and your IdP, and that your account's active SSO connection runs through the IdP app you connected to the AI client.                                                                             |
| `The user is in more than one monday account that uses this Okta app for SSO`     | Contact monday.com support.                                                                                                                                                                                                                              |

# Set up enterprise managed auth with Okta

Configure Okta Cross App Access so a supported AI client connects to monday MCP through your Okta single sign-on.

Okta supports [enterprise managed auth](https://developer.monday.com/api-reference/docs/mcp-enterprise-managed-auth) through [Okta Cross App Access (XAA)](https://help.okta.com/oie/en-us/content/topics/apps/apps-cross-app-access.htm). In XAA terms, monday.com is the resource app and the AI client is the AI agent (the requesting app).

# Before you start

* Your monday.com account meets the requirements in [Enterprise managed auth](https://developer.monday.com/api-reference/docs/mcp-enterprise-managed-auth), and its SAML SSO runs through an Okta app. That app is the one you configure below.
* You have an Okta admin who can manage apps and AI agents, and an admin for your AI client.
* Your AI client is registered in Okta as an AI agent, and your members sign in to it through Okta. Follow your AI client's documentation and [Configure AI agent-to-app with Cross App Access](https://help.okta.com/oie/en-us/content/topics/apps/apps-manage-cross-app-access.htm).

***

# Step 1: Enable Cross App Access on the monday.com app

You do this once, whichever AI clients you connect.

1. In the Okta Admin Console, go to **Applications and Resources** > **Applications** and open the app that runs your monday.com SSO.
2. Go to **Machine Assignments** > **Callers**.
3. Click **Edit** next to **Cross App Access (XAA)**, select **Enable**, and set the fields:

   | Field              | Value                         |
   | :----------------- | :---------------------------- |
   | Issuer URL         | `https://auth.monday.com/mcp` |
   | Audience/tenant ID | `https://auth.monday.com/mcp` |
   | Scopes             | Leave empty                   |

   If your app is the **monday.com** app from the Okta Integration Network, the issuer and scopes are already set. Keep the defaults.
4. Click **Save**.

# Step 2: Connect the AI client to monday.com

Repeat this step for each AI client.

1. In the Okta Admin Console, go to **Directory** > **AI Agents** and open the AI agent for your AI client.

2. Go to **Resource connections** and click **Add resource connection**.

3. Set the fields:

   | Field                              | Value                                          |
   | :--------------------------------- | :--------------------------------------------- |
   | Application instance               | The monday.com app from Step 1                 |
   | Client ID registered in monday.com | The AI client's client ID from the table below |
   | Resource identifier                | `https://mcp.monday.com/mcp`                   |
   | Scopes                             | **Allow any scope**                            |

4. Click **Add**.

5. Assign the members who should use monday.com in the AI client to both the AI client's app and the monday.com app in Okta.

| AI client | Client ID registered in monday.com                  |
| :-------- | :-------------------------------------------------- |
| Claude    | `https://claude.ai/oauth/mcp-oauth-client-metadata` |

# Step 3: Turn on enterprise managed auth in the AI client

An admin of the AI client turns on EMA for the monday.com connector (`https://mcp.monday.com/mcp`). Follow the client's own guide:

| AI client                          | Guide                                                                                                                                                          | monday.com notes                                                                                                            |
| :--------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------- |
| Claude (Team and Enterprise plans) | [Authorize MCP connectors for your entire organization](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization) | Set up **Managed authorization** on the monday.com connector. On the **Scopes** step, select all monday.com scopes or none. |

Members covered by your Okta assignments can then use monday.com in the AI client after they sign in with SSO. They don't need to connect it themselves.

***

# Turn it off in Okta

* **For one AI client:** on the AI agent's **Resource connections** tab, deactivate or remove the connection to monday.com.
* **For all AI clients:** disable **Cross App Access (XAA)** on the monday.com app.
* **For one member:** unassign the member from the monday.com app or the AI client's app.

These changes stop new connections within a few minutes. An access token that monday.com already issued stays valid until it expires, up to 24 hours.

***

# Troubleshooting

For error messages and fixes, see the troubleshooting table in [Enterprise managed auth](https://developer.monday.com/api-reference/docs/mcp-enterprise-managed-auth).

If your Okta org uses a custom domain, `The assertion is invalid` also covers the account and member checks. When you see it, also confirm the monday.com requirements and that your monday.com SSO runs through the same Okta app you connected in Step 2.
